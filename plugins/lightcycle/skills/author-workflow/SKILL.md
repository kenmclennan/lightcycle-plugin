# Co-design a lightcycle workflow

A **workflow** is how lightcycle composes many ephemeral agents into a durable pipeline: a graph of **stages** (each an autonomous agent, or a human gate), where a stage's **outcome routes to the next stage**, plus **hooks** that inject outcomes from events outside any agent (a PR merged, CI failed, a comment landed). This skill helps you and a human **shape** that graph. It deliberately does **not** carry the full grammar - once the design is agreed, the `workflow-authoring` pipeline builds the actual bundle, and its own steps carry the authoring craft.

## What to settle in the design conversation

- **The stages, and who runs each.** An **agent step** (autonomous, does the work) vs a **human gate** (a decision only a person makes - a review, a merge) vs an **engine-owned stage** (the engine runs it on its own tick with no agent, such as `poll-ci` or a script stage) vs a **fileless terminal** (a reached endpoint, no work). Name each stage by what it does, terse.
- **The review gates (phases).** A phase is one ordered gate with its own PR and worktree. Where are the human review points? `spec-driven` has two (the spec PR, then the code PR); a simpler flow has one. Decide them - they are where the human's attention lands.
- **The outcomes and routing.** What can each stage end as, and where does each outcome go? The happy path is one route; a rework loop (a review `rejected` routing back to the build stage) is another. Every way a stage can end needs a destination.
- **Whether the flow runs once or loops - and if it loops, where one traversal ends.** A **phase** is one PR gate; a **pass** is one traversal of the whole workflow. They are orthogonal, and conflating them is the usual mistake: a delivery loop with three phases might run one pass through them per work item. Most flows run once and need nothing said - one pass, closing with the item, which is `spec-driven`. A looping flow must declare the stage and outcome that close a pass, or every traversal accumulates into pass 1 and the phase runs it opened are never torn down.

  **This is the one thing the design must state that nothing downstream can infer.** A back-edge is not a boundary. `spec-driven`'s `spec-await-merge changes spec-writer` returns to the entry stage as a rework round; a looping flow whose final stage returns to its planner on `done` also returns to the entry stage, and starts a new pass. Identical shapes, opposite meanings - only the person designing it knows which they meant. The engine refuses a boundary that names a stage or outcome that does not exist, but it cannot tell anyone that one is missing. Settle it here, in the conversation, and mark it on the design mermaid.

- **The triggers.** What external events drive the flow - a PR merging, CI failing, a review comment? These are **hooks**. The **edge-vs-hook line is the one distinction that matters most**: an **edge** is an outcome the _agent_ emits (`lc done ... <outcome>`); a **hook** is one the _engine_ injects from an event. An agent never emits a hook outcome. Keep them straight when sketching the flow. A review comment drives a flow only when its author is in the operator's `trusted-authors`; other authors' comments are held. A bundle cannot declare trust, so a design that relies on a bot reviewer must tell operators to add the bot's login.
- **Whether the entry stage can conclude nothing is owed, and what gate that lands on.** `spec-writer` and `design-workflow` can end `no-change`, which routes to `nochange-open-pr` and then `nochange-await-merge`; merging that PR completes the item. A filed workflow design can end this way too, so decide whether the flow needs that exit and what the operator sees at its gate.
- **Where a moved PR head goes back to.** Every PR gate has a `pr_head_moved` route: when the PR's head changes under the gate (a push, a rebase), the engine fires `head-moved`. Decide its destination for each gate. `spec-driven` sends a spec gate back to itself, and sends the code gate back to `poll-ci` so CI runs against the new head.
- **Whether any stage repeats, and what breaks if it does.** A workflow that loops - a rework edge, or an outer loop over many work items - runs some stages more than once per item, and engine state divides sharply into what is pass-scoped and what is not. **Pass-scoped, and therefore safe to repeat:** a phase's branch, its PR, and that PR's comment ledger all live on the phase run, so the second pass through a phase gets its own and can never resolve back to the first pass's already-merged PR. Teardown is pass-scoped too - which is what the `pass-end:` boundary is for, and why a looping flow that omits it never tears anything down. **Item-scoped, and therefore stale or wrong on the second pass:** every artifact (a `spec` or a `findings` the repeating phase produced is still the first pass's unless the step replaces it), and `pr_conflict_cap`, a lifetime total across the item - so `pr_conflict_cap 3` on a looping flow trips on the third merge conflict the item has ever had. `ci_failed_cap <stage> <outcome> <N> <target>` and `review_rounds_cap` instead count a consecutive streak of that outcome at one stage, and any other outcome there resets it. Decide at design time which stages repeat, and for each, which side of that line its state falls on. A loop is not free, and the cost is paid by whoever operates it.
- **What each terminal actually does.** A stage with no outgoing route is not merely an endpoint - completing it cascades: it can close the item and delete every branch the item recorded, local and remote. Each terminal outcome also maps to `completed` or `abandoned` in the bundle's `disposition:` block, so state each terminal's disposition in the design. An escalation gate is the usual case, and it is the worst one to discover by accident, because the operator reaches it precisely when something has already gone wrong. Say so in the design for every terminal, and say what the operator is expected to do there.
- **Where a person must look at something, not just read a diff.** If a phase produces a rendered screen, a report, or anything whose defect is visible rather than textual, the design has to say so and the step has to produce it as a deliverable. A review that only reads a diff will not look at the thing - which is how three gates once passed a screen rendering raw JSON. A disposition ("verify against the rendered output") does not survive contact with a reviewer answering a different question; an artifact it must hand over does.
- **Whether the workflow carries its own tooling, and what it must own.** Reach for a **script stage** (a step file naming `script: scripts/<file>`; engine-owned, no agent, no tokens) when a stage only talks to an outside system and its result is one of a few known outcomes - polling a queue, calling an API. Keep an agent step when the stage needs judgement. A **script guard** (`guard: script:scripts/<file>` in a `schedule:` block) decides whether a schedule files an item. A **lifecycle hook** (`install`, `upgrade`, `maintain` with a `cron`, in a `lifecycle:` block) sets up or tends state outside any item. A script is at-least-once, so the design must say how it stays idempotent. The design must also name three things the workflow owns:
  - **State.** What lives in its data directory (`<data_root>/workflow-data/<origin>/<workflow>/`). The engine keeps it across upgrades and `lc workflow rm`, never decides what is in it, and only `lc workflow purge` removes it. A script writes nowhere else, except in the item's worktree when the stage declares a workspace.
  - **Config keys.** Each key the workflow reads, `required` or `optional`, with a `config-example` value. The operator sets them in the `workflow-<origin>-<name>:` block of the config file. Secrets go there, never in the bundle.
  - **Dependencies.** What the machine needs for the scripts to run (a binary, a login). An `install` hook is where a missing one is detected and the install refused.

  Installing such an origin means trusting its code, so say what each script touches. `lc workflow check` validates the block and each `script:` path, and `lc workflow simulate` walks every outcome from a fixture per script, never running the script.
- **The design checklist.** Mark exactly one `primary` edge for each stage that has a forward path. Give every owned stage a `display:` phrase. A needed engine change goes in a `## Coupled change` section, because `workflow-authoring` builds against one repo.
- **The design mermaid.** The output of design is a mermaid flowchart of the graph plus a one-line description of each stage, gate, and trigger - reviewed (on a spec PR) before anything is built.

## What NOT to do from this skill

- **Do not hand-write the bundle** (the graph markdown + the step prompts) from memory. That is the pipeline's job, and getting the exact grammar/hook syntax right is where it goes subtly wrong.
- **Do not assume the contract frontmatter enforces what it appears to.** A step with no required inputs reads as an independently-startable entry, and that context is intersected into everything downstream - so an artifact produced mid-flow cannot be marked `required` by a later stage on that basis alone. The workflow's `provides:` header covers the case: `spec-driven` declares `provides: spec`, and `write-code` accepts `spec: required`. Declare such an artifact there, and design the rest of the ordering into the graph, not into `accepts:`.
- **Do not design a step's idempotency around stored state.** A step that asks "have I already done this?" must resolve the answer from the authoritative external source - the branch, the PR, the remote - not from an artifact the last pass wrote. The artifact is a cache, and a cache is only correct if something scrubs it, which is not guaranteed for any stage that a pass may skip.
- **Do not sketch a step prompt from memory of the CLI.** A bundle's `steps/*.md` are gated at pull time: `lc workflow add`/`upgrade` read every `lc` call and JSON field read in them against the engine doing the pull and refuse the whole origin if one names a command, flag, state or field that does not exist. The same gate refuses broken step structure: a restarted top-level numbered list, an indented `@include`, and an `@include` that names no fragment. An origin may ship its own `fragments/`, which are carried into the pinned bundle, but the engine's fragment wins a name clash, so an origin fragment sharing an engine fragment's name is shadowed. That gate is the pipeline's to satisfy, not this conversation's - but it is why the design says what a stage produces and decides, never what it types.
- **Do not put stack-, repo- or environment-specific rules into a step.** `review-workflow` refuses any rule that is not true for every user of the workflow. Such a rule belongs in the target repo's `CLAUDE.md`, or in a guidance entry with `applies-to` facets. Decide this at design time, when settling what goes into steps.
- **Do not reconstruct the grammar or hook catalog here.** The authoritative reference is the **built-in bundles** (`lc workflow list` names each origin and its pinned sha; the bundles are unpacked at `$LC_HOME/workflows/<origin>/<sha>/` - read `spec-driven.md` and its `steps/*.md`) and `lc workflow describe <origin>/<name>` (add `--mermaid` for the rendered graph). Installed bundles may hold `fragments/`. Step files contain `@include plain-language`, which the raw file does not resolve; `lc peek` shows a stage resolved. The official origin keeps shared blocks in `shared/`, with a manifest and a CI drift check, so edit the canonical file first, then every copy.

## To actually build the design

File it as an item on the **`workflow-authoring`** workflow, with its `repo` set to a workflow-origin repo. The pipeline's design/build/review steps carry the full craft, author the bundle, and gate it with `lc workflow check`; a worker may run only `lc workflow check --dir .`, while `simulate` and `describe --mermaid` run in the origin's own CI and confirm the built graph matches the design. So the target origin needs that CI, a GitHub remote and a project registration (`workflow-authoring` requires a repo). You shape the flow here; the pipeline builds and proves it.
