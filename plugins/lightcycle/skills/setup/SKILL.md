# Set up lightcycle

This is the one-time onboarding for a machine. A machine that is already set up and has just had its engine upgraded needs the `upgrade` skill instead, which walks what `lc doctor` reports the upgrade left behind. The plugin's SessionStart hook has already installed the `lc` engine (pipx) and run `lc init` (seeding `~/.lightcycle`, creating and registering the `specs` and `guidance` projects, and seeding `trusted-authors` from your `gh` login only when `gh` is authenticated - on a fresh machine it usually is not yet, so the "Trusted authors" section below re-checks it; it pulls the built-in workflow origin only if `workflows-remote` is already configured, which a fresh install is not - step 1 below covers getting it configured); this skill does the interactive rest - prerequisites, config, registering repos, an optional personal workflow origin, starting the pool - and then hands off to the `driver` skill for actual work.

**Drive the safe commands yourself; hand back only for what you cannot do.** Run the read-only checks and the `lc` commands directly, and act on what they show. The only two things you cannot do for the human are a **browser login** (`gh auth login`, signing into a Claude subscription) and an **interactive editor** - surface the exact command for those and wait. Work one step at a time; confirm before writing anything. No emdashes.

## 1. Health and prerequisites

Run `lc doctor` (store, pins, contract, workflows, config, orphans, teardown, facets, guidance and github health) and check the prerequisites the bootstrap cannot establish:

- `command -v lc` / `command -v pipx` / `command -v git` - present on PATH.
- `gh auth status` - authenticated (needed for PR steps and for cloning private repos on demand).
- `git config user.name` and `git config user.email` set - `lc init` (when it creates the guidance repo) and `lc workflow init` refuse without them.
- `claude` signed in to a Claude subscription (workers bill to it) - run `claude` once to confirm.

Report a short checklist of pass/fail. For anything failing, give the exact fix; for the two logins (`gh auth login`, the Claude subscription) you cannot run them - surface the command and wait for the human to complete it.

`lc doctor` reports a `"config"` problem naming `workflows-remote` when it is set but blank - a fresh install has no default anymore. If present, ask the human for their workflow source URL, set it first with `lc config set workflows-remote <url>`, then run `lc workflow add <url> --name lightcycle` (`lightcycle` is the seeded default origin name). `lc workflow add` alone does not set `workflows-remote`, so `lc doctor` stays unhealthy.

## 2. Confirm config

Run `lc config` and show where `projects` points (default `~/workspace/projects`; `lc config get projects` prints just that). Run `lc project list` (identity, shortcode, path and facets - no remote) and show the `specs` and `guidance` projects' paths, then `lc specs-dir --check` and `lc guidance-dir --check` to verify each repo's `origin` matches its registered remote. If they are correct and the directories exist, move on. If `projects` needs changing, propose the concrete value, confirm with the human, then run `lc config set projects <path>`, which validates the value before writing it. Do not invent values; ask if unsure.

**Moving a repo, `specs` and `guidance` included.** Never `lc project rm` then `add`: that loses the shortcode and facets and strands worktrees. Run `lc project mv <identity> <new-dir>` (`lc project mv specs <new-dir>`, `lc project mv guidance <new-dir>`). It refuses while a step is running in the repo, moves the folder, repairs its worktrees, keeps shortcode and facets, and rewrites config values under the old folder (`guidance-path`, `specs-path`, callout commands). `<new-dir>` must not exist yet and its parent must. For every repo under a folder, run `lc project mv --prefix <old-dir> <new-dir>`. If you already moved the folder by hand, run `lc project set <identity> --path <new-dir>` instead (it refuses while the old path still exists). `lc project add` accepts the `guidance` identity, so no repo needs `lc init` to come back. On a fresh config, set the paths with `lc config set specs-path <path>` and `lc config set guidance-path <path>`. The required config key `context-artifact-project` names the registered project whose `filepath` artifacts resolve against (seeded as `specs`); keep it pointing at the project you moved.

**The guidance repo.** `lc init` creates and registers one, with the `guidance-shortcode` id prefix (seeded `GDN`) so `--project guidance` mints ids (default `~/workspace/agent-guidance`; `lc init --guidance-path <dir>` overrides it); `lc guidance-dir [--check]` prints the registered path and verifies its `origin`. If `lc guidance-dir --check` or `lc specs-dir --check` fails because the repo gained an `origin` after it was registered, re-run `lc init`: it reads each repo's `origin`, stores it when it differs from the registered remote (empty included) and prints `<repo>: remote updated to <url>`. To move it, use `lc project mv guidance <new-dir>`. To adopt a team's shared guidance repo instead: `lc project rm guidance`, clone the repo to the target path, then `lc init --guidance-path <dir>`.

## Trusted authors

`trusted-authors` is the list of GitHub logins whose PR comments the pool acts on; blank, it acts on none. `lc init` seeds it with your `gh` login only when `gh` is authenticated, and never overwrites it - and the SessionStart hook runs it before you have done `gh auth login`, so it may be unset. `lc doctor` reports a blank one as `required config key 'trusted-authors' is set but blank`.

1. Once `gh auth login` is done, re-run `lc init` (or run `lc config add trusted-authors <login>`) and confirm with `lc config get trusted-authors` that it holds your login, before the pool starts.
2. Ask which teammates and review bots to add (for example Copilot, which takes both logins: `Copilot` for its line comments and `copilot-pull-request-reviewer[bot]` for its reviews). A review bot can post under more than one login, so check the authors on its real comments. No bot is trusted by default. Add each with `lc config add trusted-authors <login>` (`lc config remove trusted-authors <login>` takes one off) - never set it in a workflow bundle. A bot also needs `lc config add review-bots <login>`: only a bot in both lists routes without `@lc`, and a bot in `trusted-authors` alone needs `@lc` like an operator. Every trusted human's comment, yours included, acts only when it carries `@lc`. For a bot whose summaries are only noise, offer `lc config add ignored-authors <login>`: its comments are then dropped before any routing. `lc doctor` warns when a login is on `ignored-authors` and also on `trusted-authors` or `review-bots`.
3. Explain held comments: a comment from an untrusted author becomes an `HLD-` item. A top-level comment or review is triaged first by an agent step (`held-comment-triage-timeout`, seeded 900 seconds; `0` turns triage off), and one that asks nothing is closed `noted` with no gate. Otherwise the item holds a `review-held-comment` step in `lc inbox`; the human decides it, and `lc done <step> dealt` closes it once handled (`approve` is retired; to act on the comment, post a top-level `@lc` comment on the PR).

## 3. Register your repos

A project in lightcycle is its GitHub identity (`owner/name`) in the registry; an item's `repo` artifact resolves through it. Register the repos on this machine:

1. `lc project scan --json <dir>` (default the current directory) - it walks the tree, finds git repos, and reports each as a candidate with its `identity`, `path`, proposed `shortcode`, `status` (`new` / `already-registered` / `no-remote` / `unreadable`), and `suggested_facets` (a list of `{facet, file}`). Ask the human which directory to scan if the current one is not their workspace.
2. Show the human the `new` candidates (and note any `no-remote` ones it could not identify, any `unreadable` ones git could not read, and any `already-registered`). Skip the specs and guidance repos: scan lists them as `new` although they are already registered as `specs` and `guidance`, and registering them again duplicates them. Ask which to register - do not bulk-register silently.
3. For each chosen candidate: `lc project add <identity> --path <path>`. Pass `--shortcode <X>` only if the human wants a prefix other than the derived default (the identity's trailing segment, uppercased). `scan` never registers anything itself; this step does.

An entry can also name a project directly with `applies-to.projects`; facets remain the way to aim guidance at a kind of project. Facets tag a project for guidance: `lc project add <identity> --path <path> --facets a,b,c` sets them at registration, and `lc project set <identity> --facets a,b,c` changes them later. A facet is valid only if the guidance repo has a `<facet>.md` concept page; `lc doctor` flags one that does not. `scan` suggests facets for each repo (conventions v4+): a concept page in the guidance repo may carry a `detected-by` list of file names or globs, and a facet is suggested when one matches a tracked file, shown with the file that matched. When no page carries `detected-by`, scan prints one `no facet suggestions: <reason>` line. Treat suggestions as proposals to show the human; scan sets nothing, so apply the chosen ones with `--facets`.

A repo that lives outside the scanned tree can be registered directly with `lc project add <owner/name> --path <dir>`. A registered repo you have not checked out here is cloned automatically when you activate an item that targets it - no need to clone it now.

## 4. Offer a personal workflow origin

Ask whether the human wants their own workflow origin (a pullable repo of their own `lc` workflows, separate from the built-in `lightcycle` one). If yes, `lc workflow init <name>` scaffolds it at `<projects>/<name>`, registers it as a writable source, and sets it as the personal origin. It is local only: no GitHub remote and no project registration. To build in it through `workflow-authoring`, add a remote and run `lc project add` for it. To adopt an origin that already exists, run `lc workflow add <url> --writable`; toggle later with `lc workflow set <origin> --writable|--read-only`. If they only need the built-in workflows, skip this.

A workflow can declare config keys of its own. `lc doctor` reports a required one that is missing or blank as `workflow <origin>/<name> needs config key '<key>' in block '<block>'`. The block is named `workflow-<origin>-<name>:` and is set with a dotted key, like a `schedule-<id>` block: `lc config set workflow-<origin>-<name>.<key> <value>`. Ask the human for each value, never invent one, and confirm with `lc config get workflow-<origin>-<name>.<key>` and `lc doctor`. Adding such an origin runs the workflow's `install` hook first. If `lc workflow add` fails, the origin is not registered: read the command's output (the hook's output is shown as a 2000-character tail, and the failure names the full run log), fix the cause it names, and re-run. `lc workflow list` shows what was registered.

## 5. Start the pool

Run `lc start --detach` to start the pool in the background, or `lc tui --start` (engine 0.6.299+) to start it and open the dashboard. Mention `developer-mode` (`lc config`) only for a machine that develops lightcycle itself.

**Scheduled audits.** A fresh config enables four schedules, `retro-audit`, `material-audit`, `daily-summary` and `ratchet-sweep`, run in the `guidance` project's repo and file their items under a purpose name as project: `audit` for the retro audit, the material audit and the ratchet sweep, `summary` for the daily summary. `lc schedule list` shows both, the registered `project` the work runs in and, as its last column (`name` in `--json`), the purpose name (`-` when a schedule has none). Show them with `lc schedule list` (each reads `on`, `off` or `paused`, with the reason) and check `lc config get schedules-paused`: while it is `true` the pool files nothing. To run one on demand, use `lc schedule run <id>` (see the `driver` skill). Once the pool runs, `AUD` items (the audits and the Monday ratchet sweep, whose `repos-active` guard files nothing when it fails) and `SUM` items (the daily summary) start appearing, and their findings surface in `lc inbox`. They resolve only after `workflows-remote` is set and the `lightcycle` origin is pulled (step 1), so a machine that skipped that sees them stay unresolved; `lc doctor` flags a schedule naming a workflow it cannot resolve. Some workflows ship a suggested schedule that `lc schedule list` shows as `off - bundle suggestion`; list any such rows and offer each to the human, and never enable one unasked. A suggested schedule's guard may need parameters set in its `schedule-<id>` block (`bump-engine-pin`'s guard needs `repo`); without them it warns every firing and files nothing. An existing config gets no seeded blocks - there `lc doctor` reports `schedule-not-enabled` instead.

**Gate callouts.** A callout is an executable the engine runs when a human gate opens, to add a view or link to its Detail tab. Configure one as a `callout-<id>` block, setting every key with `lc config set callout-<id>.<key> <value>` (`lc config unset callout-<id>` removes the block): `command` (one executable path), `subject` (`pr`, `description` or `artifact:<name>`), `principal-outputs` (comma-separated names of the principal outputs it runs on), `wait` (`true` holds the gate out of `lc inbox` until it finishes) and `timeout` (seconds). A callout runs at a gate only when `subject` matches what the gate presents and the gate's principal output (what its authoring steps produce, such as `spec`, `feature`, `code`, `workflow` or `guidance`) is in `principal-outputs`: a spec view lists `spec`, a review view lists `code`, and `spec, code` runs on both. The key has no default, so a block without it never runs and `lc doctor` reports it as `callout-invalid`. Saving prints a warning and a `fix:` line for any preflight problem. Check it with `lc doctor`, which runs each callout's preflight and reports a bad block as `callout-invalid` and a failed preflight as `callout-preflight`, each with its fix; the operator applies the fix. A callout may report its spend in an optional `usage` field of its response, which the engine adds to the gate step's cost, and it answers a `cleanup` verb after the gate closes (it never holds the gate, and a failure shows only as a condition note on the step). To write the executable itself, read `references/callout-functions.md`.

**Editing config later.** Change one key with `lc config set|unset|add|remove`; keep `lc config --edit` for a bulk edit of the whole file. A running pool reloads the config file within a tick and prints `config reloaded`, so edits apply without a restart. The exceptions are the four restart-required keys, `poll-seconds`, `pool-upgrade-check-seconds`, `tick-failure-cap` and `spin-cap`: after one changes, the tick line says `restart needed for: <keys>` and `lc doctor` reports it. An invalid edit is rejected and the last good config stays in force; `lc doctor` reports it.

## 6. Hand off to the driver

Setup gets the machine and repos usable; it stops there. The first actual item - developing a brief, filing it, clearing the review gates - is the `driver` skill's job. Point the human at it: invoke the `driver` skill to start driving work.

## Boundary

This skill is machine-level onboarding only. It does not develop briefs, file items, or run the pipeline - that is `driver`. It does not author workflows - that is `author-workflow` and the workflow-authoring pipeline. Re-running it on an already-configured machine is safe: every step is a check that reports "already done" and moves on.
